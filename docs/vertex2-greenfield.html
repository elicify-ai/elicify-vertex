elicify-vertex · greenfield design · v2 proposal

From guardrail to exoskeleton

Vertex 1 is a system of gates: it stops bad endings. The behavior users actually love — ownership, one-shot competence, root-cause instinct, taste — is initiative, and initiative cannot be gated into existence. Vertex 2 keeps the gates as the last line and rebuilds everything in front of them: a phase-aware process engine, an injection layer that prescribes instead of complains, and prompt techniques that motivate reasoning, not compliance.

00

Why v1 plateaus

Three structural limits — not bugs, design ceilings.

limit 1

It complains, it doesn't coach

"Files changed, no verification observed — run a test." True, and useless. The harness knows which files changed, which verifier last ran, and what it covered — and throws that away at the exact moment it matters.

limit 2

It regulates the end of the turn

The stop gate fires at idle. But quality is decided at the start: whether intent was restated, assumptions surfaced, an approach chosen. v1 has zero presence where one-shot competence is born.

limit 3

Process is passive

The goals engine waits to be invoked, stories are free text, checkpoints accept prose as evidence. The plan never talks to the injection layer. It's a notebook, not a backbone.

Thesis. One loop, seven phases, three injection moments. Every injection follows one grammar: Observation → Diagnosis → Prescription → Example. The goal engine carries the state that makes prescriptions specific. Gates remain — as the last resort, and every block teaches.

01

The loop — seven phases, three injection moments

Work moves through phases. The engine tracks the phase per story and serves phase-matched guidance. The right prompt at the wrong phase is noise.

phases 1–3 · front-load

Where one-shot competence comes from

Restate the real outcome in one line. Pin acceptance criteria. State 2–3 assumptions and proceed — ask only at irreversible forks. Name the approach and the approach you rejected. For multi-story scope, the engine proposes the decomposition unprompted.

phase 6 · elevate

Where "done" becomes senior

Fires once, after the verifier goes green: replay each acceptance criterion against evidence; sweep adjacent findings (surface always, fix if small + same root cause + tested, else propose); one taste pass — read the diff as a reviewer who didn't write it.

02

The injection grammar — prescribe, don't complain

Every injection is generated from observed state and follows one shape: Observation → Diagnosis → Prescription → Example. If the harness cannot fill all four slots, it should question whether it has anything to say.

v1 — complaint
[vertex:stop-block] Files were changed this turn but no successful verification command was observed. Run the narrowest relevant test, lint, typecheck, build, check, validate, verify, or HTTP probe now and cite its observed result.
v2 — prescription
[vertex:verify-gap] Observed: src/parser.ts, src/lexer.ts changed. Last verifier `tsc --noEmit` (types only) predates the lexer edit. Diagnosis: behavioral change carrying type-only evidence — logic regressions are invisible to it. Do now: npx vitest run tests/lexer.test.ts (narrowest suite covering the changed paths). Then: if it passes on the first run, state why you trust a test you never saw fail.
v1 — complaint
[vertex:repeat-failure] The same class of failure has repeated 2 times. Stop retrying silently — report what failed, what you already tried, and your next hypothesis.
v2 — prescription
[vertex:re-model] Observed: `npm test` failed twice with the same signature (TS2322 in goals.ts:114); your two edits changed the same 4 lines. Diagnosis: perturbing one location twice = the defect is probably NOT at that location. Do now: before a third edit, answer in one line: what belief about goals.ts made both fixes look right? Read the caller (index.ts:1408) before touching the file again. Example: "I assumed checkpoint() owns the receipt type — it's actually widened upstream."

Composition rules

Budget: 2 per turn

Attention is the scarce resource. Priority when over budget: correction > phase guidance > enrichment. Everything else waits or is dropped.

Cooldowns everywhere

No directive repeats within its cooldown window. A guidance system that repeats itself trains the model to ignore it.

Decay by compliance

If the model followed the prescription last time, the next occurrence shrinks to a one-line reminder. Dosage adapts to observed behavior.

03

Prompt technique library — motivate reasoning, not compliance

Ten patterns, each mapped to the failure mode it targets and the phase where it fires. These are questions that change the reasoning path, not instructions to obey.

PatternFires atTemplateTargets
Pre-commitmentVERIFY, before any run State the expected output in one line — before running."Expected: 18 tests pass, the new one fails on the boundary case." Confirmation bias. Makes surprise detectable — the anomaly interrupt keys off this.
FalsificationFRAME / new tests What observation would prove this approach wrong? Get that observation first."Break the guard, watch the test fail, restore." Coherent-but-wrong narratives; tests that can't fail.
Assumption-forwardINTAKE List 2–3 assumptions you are proceeding on. Ask only if a fork is destructive."Assuming: Node ≥20, the API is internal, breaking the CLI flag is acceptable." Clarification-loop paralysis; invisible assumptions.
Contrastive planningFRAME Name the approach you rejected, in one line, with the reason."Rejected event-sourcing: two writers, no replay need." First-idea anchoring. Forces ≥2 options at near-zero token cost.
Surprise interruptanomaly Expected ≠ observed. Revise your model of the system before touching the code. What did you believe that is now false? Rationalizing anomalies; symptom-chasing.
Root-cause ladderafter any failure→fix Symptom or defect? What allowed it? Does the defect survive your fix anywhere else? Bandaid fixes — fires on every fix, not only "debug"-classified tasks.
Confidence declarationVERIFY State confidence (low / med / high) before the verifier runs. The harness logs calibration per model. Overconfident coherence — the only pattern that catches "sincerely wrong."
Criteria replayELEVATE / CLOSE Quote each pinned acceptance criterion. Mark met / unmet, each with an evidence pointer (receipt id). Answering the literal request instead of the intent; long-horizon drift.
Rubric self-scoreELEVATE Score the diff: correct · minimal · consistent with the codebase · tested. Any low-confidence item → act on it now. Unexamined "done"; quality left on the table.
Taste passELEVATE Read the full diff as a reviewer who didn't write it. Delete anything that doesn't pay rent. Accumulated cruft; the gap between "works" and "signed by a senior."

Design rule: imperatives produce compliance theater; questions with a required one-line answer produce reasoning. Every pattern above demands a short written artifact (an expectation, a rejected option, an assumption list) — which the harness can then observe, compare against outcomes, and measure.

04

Goal engine v2 — the process becomes the backbone

You were right that goals are the mechanism — and right that v1 doesn't do it right. v1 stories are prose in a JSON file. v2 stories are contracts that the injection layer reads.

v1

Passive

Waits for the user to invoke /goal-create. Plans are an afterthought.

v1

Prose stories

Objective is free text. No criteria, no scope, no bound verifier. Checkpoints accept any string as "evidence".

v1

Disconnected

The plan never informs the injection layer. The stop gate doesn't know what "done" means for this story.

// v2 story — a contract, not a note. Written at FRAME, enforced everywhere.
{
  "id": "S2",
  "objective": "Parser handles nested templates",
  "phase": "execute",                        // intake|frame|plan|execute|verify|elevate|closed
  "acceptance": [
    { "id": "A1", "text": "nested `${}` parses to AST depth n", "evidence": null },
    { "id": "A2", "text": "error spans point at inner token",  "evidence": null }
  ],
  "scope": ["src/parser/**", "tests/parser/**"],   // feeds the scope watchdog
  "verifiers": ["npx vitest run tests/parser"],     // feeds verify-relevance + prescriptions
  "assumptions": ["grammar stays LL(1)"],
  "rejected": ["regex pre-pass: can't nest"],       // contrastive planning artifact
  "amendments": []                                    // re-planning is legal, but logged with reasons
}

What the contract buys, mechanically

Scope watchdog (guides, doesn't block)

Mutation outside scope → "src/cli.ts is outside S2. Fold it into a proposal, amend the story with a reason, or revert." Proactivity becomes visible and governed — surface always, fix when small + same root cause + tested, propose otherwise.

Verifier relevance

Green evidence must come from a verifier bound to the story (or covering its changed paths). tsc after a logic change downgrades to partial evidence — the prescription names the missing suite.

Receipt-bound criteria

A checkpoint is legal only when every acceptance item carries an evidence pointer (verification receipt id or explicit user waiver). Prose is not evidence.

The plan is the memory

The goal file survives compaction; after every compaction the engine re-injects pinned criteria + active story. Long-horizon persistence stops depending on context luck.

06

Measure what users feel

v1 counts blocks. Users don't feel blocks — they feel corrections they didn't have to make.

One-shot rate

Corrective user turns per task, from first ask to acceptance. The single number closest to "feels like Fable".

Block conversion

Share of gate blocks followed by a green, relevant verifier within the same turn. Measures whether prescriptions actually teach.

Proposal acceptance

Share of elevate-phase proposals ("I also found X — take it?") the user accepts. Proxy for assessed, non-annoying proactivity.

Criteria-met-at-close

Acceptance items with hard evidence at checkpoint ÷ total. Detects literal-answer-wrong-intent.

Calibration

Declared confidence vs verifier outcome, per model. The overconfident-coherence detector.

Directive ROI

Per directive family × model: compliance rate and downstream outcome delta vs holdout. Prompts that don't move outcomes get deleted.

The honest ceiling, stated up front: this system closes the discipline gap — front-loading, persistence, root-cause, evidence. It narrows but cannot close the judgment gap: taste and true one-shot competence remain properties of the base model. The exoskeleton makes a mid model work like a disciplined senior; it makes a frontier model auditable. Both are worth building.

08

Implementing the guide layer — the three-tier composer

The obvious question: doesn't "diagnose and prescribe" need an LLM verifier? Mostly no — and where judgment is genuinely needed, extract it from the working model itself, pinned in time so it cannot be rationalized. A verifier model exists only as a thin escalation tier.

tier 1 · always

Deterministic slot-filling

~80% of guide value, zero LLM. Observations come from the ledger. Diagnoses come from a finite failure-mode taxonomy — each taxon a template with slots. Prescriptions come from narrowest-verifier resolution: story verifiers → basename matching (src/lexer.ts → tests/**/lexer.test.ts) → rg in test dirs → package.json scripts → vitest related. Fast, free, debuggable, never hallucinates.

tier 2 · the real verifier

Temporal self-judgment

"Was this expected?" needs no verifier — it needs pre-commitment. The harness demands EXPECT: <one line> before the run (captured deterministically from the text stream), then compares expectation vs observation with string/exit logic. The verifier is the working model at time T, audited at time T+1 — judgment extracted before the outcome exists cannot be rationalized after. Same mechanism: confidence calibration, criteria replay (every "met" must carry a receipt id), root-cause ladder.

tier 3 · escalation only

LLM verifier, on a leash

Needed for three things only: intent-vs-criteria audit at the final gate of deep stories, classifying failures the taxonomy misses, scoring taste passes for measurement. Constraints: runs as an in-loop subturn — a child session (session.create({parentID})) prompted with tool-calling disabled, on the session's own model — always configured, and deliberately the same model as the worker (2026-08-06: the optional verifierModel override and its fallback chain were removed — backlog B-1, spec FR-030a), 5 s cap, never in the hot path, deterministic fallback, and an evidence-only diet — diff + criteria + verifier output, never the chat narrative, or the verifier inherits the coherence bias it exists to catch.

Which tier implements which guide feature

The principle: the guide layer's intelligence is state you already collect, kept until the moment it matters, poured into templates — plus the working model's own judgment, extracted before outcomes exist so it is checkable after. A second model verifies only what the first model cannot be pinned to: intent. Graceful degradation top-down: tier 3 unavailable → tier 2 still guides; tier 2 artifact missing → tier 1 still prescribes.
